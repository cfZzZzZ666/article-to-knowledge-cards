# make-knowledge-cards

一个 Codex Skill：把用户粘贴的文章或本地 Markdown / TXT 文件，提炼成 5–8 张可以直接复习的知识卡片。

## 1. 解决什么问题

读完一篇文章，当下觉得都懂了，过几天想复习时却找不到重点：铺垫、客套、作者的个人经历、口号和重复语句占了大部分篇幅，真正有用的结论、定义和因果散落在各处。

这个 Skill 把这类文章压缩成少量可以反复看的知识卡片——只留下真正重要的知识，一张卡只讲一个知识点，重复内容合并，原文里没有的信息一律不补。信息不足时它宁可少出几张卡，也不把文章"填"成好看的张数。

## 2. 主要功能

输入一段正文或一个文件，输出一组 Markdown 卡片。每张卡固定四项：

| 卡片项 | 内容 |
| --- | --- |
| 标题 | 一句话说明这张卡讲什么 |
| 核心知识 | 一个知识点，一句话陈述结论 |
| 简明解释 | 2–4 句，说清它是什么、为什么成立或怎么用 |
| 例子 或 自测 | 二选一：原文中的具体例子、数据或场景，或一个答案能从原文得出的自测问题 |

具体的提炼行为：

- **只留重要的**。保留核心结论与原理、关键定义与术语、因果关系及其条件、方法或步骤的骨架、易混淆概念的区别、带数字或条件的判据；为理解核心结论所必需的定义、公式和数值即使像常识也保留。
- **丢掉次要的**。丢弃背景铺垫与客套、作者的个人经历和情绪、修辞口号与号召、重复语句、只有细节没有结论的材料、读者本就懂的常识，以及只报结果不含做法的效果陈述（例如"推送从 8 分钟降到 40 秒"）。
- **一张卡一个知识点**。重复、同义、换个说法的内容合并成一张卡；标题里出现"和 / 以及 / 与"这类并列词通常说明该拆成两张。
- **不编造**。每条信息都要能在原文找到依据；"简明解释"只能把原文的说法换个讲法，不补充原文没有的机制、因果链或对比；例子优先用原文已有的，原文没有例子就改成"自测"，问题也不引入原文没有的数字或场景；原文含糊或带条件时保持同样的限定，不替原文下更强的结论。
- **数量可控**。默认 5–8 张；候选知识点多于 8 个时按重要度取前 8 个；少于 5 个时出多少算多少并说明有几个，绝不凑数；用户明确要求张数时以用户要求为准（可以超出 5–8），但同样不靠次要内容凑数。
- **输出干净**。默认在回复里直接给出 Markdown 卡片，只输出卡片本身，不追加点评、延伸阅读、学习计划或额外的"总结卡"；卡片正文语言与原文一致、不翻译，四项标签默认保持中文，原文不是中文时也可译成原文语言（但四项齐全、顺序一致）。

暂不支持：网页抓取、PDF、图片、幻灯片、Anki 导出、图形界面。遇到这类输入时，Skill 会说明限制并请你改贴纯文本或提供 `.md` / `.txt`，不会尝试去抓取或转换。

## 3. 安装方法

把 `make-knowledge-cards/` 整个目录复制到 skills 目录，下次会话即可使用：

- macOS / Linux：`~/.codex/skills/`
- Windows：`C:\Users\<用户名>\.codex\skills\`

发布到 GitHub 后，也可以由 `skill-installer` 安装（路径指向仓库里的 `make-knowledge-cards` 目录）。

Skill 本身是纯指令，没有脚本、没有第三方依赖，复制目录即可：

```text
make-knowledge-cards/
├── SKILL.md            # 提炼规则与流程
└── agents/
    └── openai.yaml     # UI 元数据（显示名、简述、默认提示词）
```

项目根目录同时是 Skill 的父目录：`README.md` 在根目录，Skill 位于同名子目录中。

## 4. 使用方法

三种调用方式，任选一种：

```text
$make-knowledge-cards 把下面这篇文章做成知识卡片：
<粘贴正文>
```

```text
把 C:\notes\http-cache.md 做成知识卡片
```

```text
用 $make-knowledge-cards 把 D:\notes\article.txt 转成知识卡片，给我 6 张
```

默认输出在对话里；说了"保存到 `C:\notes\cards.md`"才会写文件。只给出输入文件路径时，卡片仍然直接回复给你。

## 5. 输入输出示例

### 示例一：粘贴短文，原文知识点不足 5 个

输入：

```text
用 $make-knowledge-cards 把这篇文章做成卡片：
双因素认证（2FA）要求用户提供两类不同性质的凭证：一类是知道的东西，例如密码；
另一类是自己拥有的东西，例如手机上的动态验证码或硬件密钥。这样即使密码泄露，
攻击者仍然缺少第二类凭证，无法直接登录账号。
需要注意的是，短信验证码属于较弱的形式，因为它可能被 SIM 卡劫持或拦截。
```

输出（3 张卡，没有为了凑够 5 张而搬常识）：

```markdown
原文中真正重要的知识点只有 3 个，因此少于 5 张，不补足。

## 1. 双因素认证要求两类不同性质的凭证
- **核心知识**：双因素认证（2FA）要求用户提供两类不同性质的凭证：一类是知道的东西（例如密码），另一类是自己拥有的东西（例如手机上的动态验证码或硬件密钥）。
- **简明解释**：关键在"不同性质"，第二类凭证不是另一串密码，而是用户实际持有的东西。
- **例子**：密码 + 手机动态验证码，或密码 + 硬件密钥。

## 2. 2FA 让密码泄露不再等于账号失守
- **核心知识**：即使密码泄露，攻击者仍然缺少第二类凭证，无法直接登录账号。
- **简明解释**：第二类凭证把"知道密码"和"能登录"拆成了两件事。
- **自测**：如果攻击者已经拿到你的密码，他还缺什么才能登录？

## 3. 短信验证码是较弱的第二因素
- **核心知识**：短信验证码属于较弱的形式，因为它可能被 SIM 卡劫持或拦截。
- **简明解释**：它的弱点来自传输和载体，而不是验证码本身的形式。
- **自测**：为什么把短信验证码作为第二因素不够安全？
```

### 示例二：给一个 Markdown 文件，知识点充足

输入：`把 C:\notes\http-cache.md 做成知识卡片`

输出 8 张卡，标题如下：

1. 强缓存靠 max-age 决定何时完全不发请求
2. no-store 与 no-cache 的区别
3. 协商缓存用 ETag / If-None-Match 验证内容
4. 另一种验证方式是 Last-Modified / If-Modified-Since
5. 服务器判定未变化时返回 304
6. 两类缓存的成本不同
7. 按资源类型分配缓存策略
8. 排查缓存问题要看浏览器实际收到的响应头

其中一张：

```markdown
## 7. 按资源类型分配缓存策略
- **核心知识**：带内容哈希文件名的静态资源（如 `app.3f9a1c.js`）可以设一年的 `max-age` 并配合 `immutable`；`index.html` 应该使用 `no-cache`，让每次访问都走协商缓存。
- **简明解释**：文件名变化本身就代表新版本，所以哈希资源可以长期使用强缓存；入口页面一旦被强缓存，用户会长期停留在旧页面上，因此必须每次验证。
- **例子**：`app.3f9a1c.js` 长期强缓存，`index.html` 设为 `no-cache`。
```

### 示例三：英文原文

输入一段英文文章后，卡片正文保持英文，四项标签默认仍是中文：

```markdown
## 1. Communication paths grow faster than headcount
- **核心知识**：Every person added to a project creates new communication paths — four people need six pairwise conversations, eight people need twenty-eight.
- **简明解释**：The number of pairwise links grows much faster than the number of people, so meetings, handoffs, and status updates consume time that would otherwise be spent building.
- **例子**：Brooks described this arithmetic in 1975 in the mythical man-month argument.
```
